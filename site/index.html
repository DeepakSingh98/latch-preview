A compiler for training megakernels

Latch is a compiler for generating training megakernels on NVIDIA H100 GPUs. We’re building it to make alternative architectures and learning algorithms easier to explore when systems engineering and execution costs would otherwise put them out of reach.

A training megakernel is a single generated GPU program that computes a model’s predictions, its loss, the gradients and the weight update. Latch is a research preview. We intend to release it as open source; the code is not yet public.

Why start with fine-grained computation

Deep learning software is built for large, regular work: big matrix products over big batches. Some learning procedures instead divide the computation into many small pieces, or make frequent updates that each depend on the one before. On a GPU each small piece usually runs as a separate kernel. When the pieces are small, starting kernels and moving intermediate results through memory can cost more than the arithmetic. A procedure can then be cheap to compute and still slow to run, and so expensive to study.

Generating one program for the whole update removes much of that overhead. It does not remove the arithmetic, and it does not make every workload faster. We began with two directions in which the overhead is large:

  • Mixture-of-experts models, especially those with many small experts. Each token is sent to a few experts, so every update consists of many small matrix products whose sizes are uneven and change from one update to the next.
  • Test-time learning, in which a model changes its internal state or weights as data arrives. Prediction and update alternate, one small step at a time.

These are starting points, not the limits of the project, and not every model of either kind will benefit.

A complete example: TinyMoE

TinyMoE-200M is a public mixture-of-experts language model with sixteen experts in each layer. To support it, we added token routing, uneven expert matrix products and their gradients to Latch, and changed how it handles attention and builds large programs (details). Latch then generated TinyMoE’s complete training megakernel: forward pass, loss, backward pass, gradient clipping and the AdamW update, in one program. Latch does not yet compile arbitrary models from Hugging Face; each new architecture needs similar work.

Faster updates matter only if they shorten training, and that is a separate question. In an earlier experiment, using a previous version of Latch, we trained TinyMoE from random initialization on FineWeb-Edu. Latch, updating on 32 sequences of 1,024 tokens at a time, reached validation loss 3.30 with 18–24% less accumulated update time than the fastest PyTorch implementation we measured of the original 128-sequence batch.

Three paired seeds: 1,428–1,468 s for Latch against 1,751–1,915 s for PyTorch, each with its own tuned learning rate. These runs predate the 12.57 ms kernel above and do not include its speed. PyTorch at Latch’s batch size is compared on the learning page.

Test-time learning

In test-time learning a model keeps learning while it reads: for each token it makes a prediction, measures the error and updates some of its weights before reading the next. The steps are small and strictly ordered, so a conventional implementation spends much of its time starting kernels. Even replayed from a CUDA graph, one 1,024-token block issues 18,176 of them.

The packaged GradLev example adapts the final MLP of GPT-2 small over a 1,024-token block. Latch runs the whole loop of 1,024 dependent predict-and-update steps as one generated kernel and keeps the adapted weights in on-chip memory throughout. The rest of GPT-2 runs as ordinary PyTorch before the loop.

Support for test-time training beyond examples like this one is still at an early stage.
