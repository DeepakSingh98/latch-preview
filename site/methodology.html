How we measure

Execution benchmarks alternate Latch and PyTorch on the same otherwise idle H100. Repeated rounds reduce the effect of changes in machine performance. Each result states its timing statistic.

We time complete training updates and adaptation blocks. A training update includes the forward pass, loss, backward pass, clipping and optimizer. For time to quality we add these update times until the model reaches a fixed validation target. Compilation, evaluation, checkpointing and data loading are outside this clock.

We compare against the fastest tested PyTorch implementation that passes the applicable checks. The standard TinyMoE control uses compiled layers and grouped expert products. Looped TinyMoE and GradLev also have CUDA-graph controls. Each case below specifies its implementation.

Numerical checks compare outputs, gradients and updates with an independent reference. Restart checks compare resumed and uninterrupted execution bit for bit. The details below each result identify the shapes and states tested.

Different batch sizes answer different questions

Holding the batch and recipe fixed isolates execution speed. TinyMoE updates are 5.1× faster at 2 × 512 tokens and 1.74× faster at 32 × 1,024. Fusion saves a larger share of the time when each operation is small.

Changing the batch changes both learning and execution. We tune each recipe and compare the tokens and time needed to reach the same target. The recipe comparison reports this separately from the execution benchmarks.

Pretraining from scratch

We pretrained TinyMoE-200M from scratch on FineWeb-Edu. Both implementations started from random weights. Latch and PyTorch used the same tuned recipe at 32 × 1,024 tokens per update. Each pair shared its initial weights and data order. All runs completed a 655M-token schedule. We measured the training-update time needed to reach validation loss 3.30. The protocol and target were fixed before training began.

Small-batch training

The small-batch benchmark measured 12.57 ms per Latch update versus 64.52 ms for PyTorch. We then tested whether that advantage persisted through full training at the same batch.

Three paired seeds (2051–2053) trained from random initialization with the release’s default recipe. Both implementations ran 640,000 updates at the same batch size, for a total of 655M tokens. Neither reached the planned loss target of 3.30. Both ended near 4.0. The protocol specified a fallback: use the lowest target reached by both implementations on every seed. That target was 4.10.

Latch reached loss 4.10 5.3–6.2× faster. The largest loss gap at equal tokens was 0.016 nats. Median update times across the full runs were 12.4–12.6 ms for Latch and 70.0–75.0 ms for PyTorch. PyTorch ran more slowly on these hosts than in the short benchmark.

Both implementations failed some numerical checks after training. The small-batch result has therefore not passed the full numerical policy.

Numerical checks

Early gradients passed the FP64-reference check. We tested updates 1 and 32 from the public weights and the first update from random weights. The largest gradient relative-L2 errors at random initialization were 0.0206 for Latch and 0.0225 for PyTorch. The limit was 0.08. Both implementations resumed bit for bit, including on a different machine.

After 320,000 updates of Latch’s seed-2051 run, four of 663 gradient tensors exceeded the same limit. Their errors were 0.083–0.089. Repeating the check on another machine gave identical results.

We then checked five predetermined cases at trained states. PyTorch received the same weights, optimizer state and batch as Latch. Latch failed two cases and PyTorch failed one. An FP64 reference using BF16-rounded operands also exceeded the limit in one case. Across 3,021 gradient tensors the mean log2 ratio of Latch’s error to PyTorch’s was +0.002. We found no implementation or harness defect. These results point to sensitivity to BF16 rounding.

PyTorch’s own state after 320,000 updates of seed 2051 passed, with a maximum error of 0.061. All tolerances stayed fixed. A change in precision or acceptance policy would need a new verification study.

Comparing learning recipes

We also compared different recipes. The earlier tuned small-batch recipe used 2 × 1,024 tokens per update and a 393M-token horizon. We ran it with the released compiler. Its control was the tuned batch-32 PyTorch recipe above. The comparison used the same three seeds and initial weights.

On the two seeds that reached the target, the tuned small-batch recipe used 15% fewer tokens: 335.5M against PyTorch’s 394.3M. It still took longer. Latch at 2 × 1,024 takes about 7.0 s per million tokens. PyTorch at 32 × 1,024 takes 4.3 s. Their update times are 14.3–14.4 ms and 139.7–142.5 ms respectively.

Batch-32 PyTorch reaches the target first on every seed. Batch-32 Latch is faster still. Small-batch Latch would need an update time of about 10.4 ms to match PyTorch at loss 3.30. At its current speed it would need about 28% fewer tokens. These are calculated thresholds.

Evidence: release-learning.json (tuned_small_batch); report research/latch_tuned_ttq/RESULTS.md on codex/latch-tuned-ttq @ 5c427c2eb; sources.

TinyMoE-200M: update-speed benchmarks

5.1× faster updates at 2 × 512 tokens. At 32 × 1024 the speedup is 1.74×.

The pretraining experiment above starts from random weights on FineWeb-Edu. The 5.1× result below comes from a separate short timing test. It starts from TinyMoE’s public weights and uses WikiText-103.

TinyMoE-200M has 199,837,056 weights. Latch runs the forward pass, loss, backward pass, clipping and AdamW in one kernel. Early-update audits and restart pass. Long-run checks at this batch expose a numerical limit.

The control compiles each layer with torch.compile and uses grouped expert products. It does not replay the update as a CUDA graph. We have not built a CUDA-graph control for this ragged-routing update.

The batch-32 recipe takes 79.9 ms per update with Latch and 139.2 ms with PyTorch. That is a 1.74× speedup. Complete training runs reached loss 3.30 with 41–44% less update time. See the training results.

At the published batch of 16 microbatches of 8 × 1024 tokens, an older measurement gave 977.2 ms for Latch and 1,088.4 ms for PyTorch. Large microbatches spread the conventional overhead across more work.

SMELT-style looped TinyMoE

1.34× faster complete training updates than compiled PyTorch with CUDA graphs.

The middle six of TinyMoE’s twelve layers run twice with shared weights. We adapted this design from the SMELT papers. We found no official code. Both implementations use the same model, objective and AdamW recipe at 32 × 1024 tokens per update.

Repeating the six middle layers adds about 34 ms to Latch and 39 ms to the conventional graph. The layers share weights but each visit still requires computation. Both implementations crossed losses 3.50, 3.30 and 3.20 at identical update counts in the research runs. Latch reached each target 1.31× sooner in update time.

The research build used the rowchain rule. We later found that this rule could cause an arena race. The package includes the fix. Its rebuilt program matches the research program bit for bit from all three tested states. Repeated runs and restarts also match.

GradLev causal adaptation on GPT-2

3.5× faster complete adaptation blocks than the strongest tested CUDA-graph control. Latch runs 1,024 dependent learning steps in one kernel. The control uses 18,176 kernels.

GPT-2 small predicts each token in a 1,024-token block. It uses the prediction error to update its final MLP before predicting the next token. We adapted this procedure from the GradLev paper. We found no official code. The benchmark measures adaptation of one MLP during deployment.

The two adapted matrices are split across the SMs. Each block owns 24 hidden units and keeps its part in shared memory for all 1,024 steps. The frozen output head occupies 77 MB. It must be read at every token.

Policy P1b computes the head’s logits, online softmax and gradient in one pass. About 23 of every 64 head row groups stay in the 50 MB L2 cache across steps. The kernel streams the other groups and prefetches the next step’s input rows. The head pass takes 24.4 µs per token.

Policy P1 instead rounds gradient weights to BF16 and uses a two-pass head. Under this policy Latch takes 90.4 ms per block. Its strongest control takes 161.3 ms. That is a 1.79× speedup.

Adaptation reduced loss in the learning study. GradLev’s extra meta-training did not improve on the same update rule applied to an ordinary fine-tune at this scale.

E2-TTT-MLP outer training: correct, but about 3× slower

The complete 424.8M-parameter update compiles and passes its numerical checks. Its tested learning trajectory matches PyTorch. It runs about 3× slower than torch.compile max-autotune.

This experiment used a research build of Latch. E2-TTT-MLP is a released language model whose layers learn a memory as they read. Training the model requires differentiation through those inner updates. Latch generated the complete outer-training update through its normal API. Its gradient error matches the published implementation. Restarts are bitwise. A 256-update continuation learned identically to the conventional implementations.

Latch divides each microbatch into about 5,000 intervals separated by barriers. Memory updates take two thirds of the time. These contain small elementwise operations and reductions that Inductor combines into far fewer kernels.

Latch also retains every saved activation in its arena. The published microbatch of four sequences needs a 77.6 GB arena. With the model and optimizer state it does not fit on an 80 GB H100. An isolated layer’s memory update takes 4.19 ms with Latch and 5.48 ms conventionally at one sequence. At four sequences it takes 11.14 ms and 7.10 ms respectively.

A further-tuned Latch build reached 8.79 s. This was still 2.8× slower than its control. It used the old rowchain rule and was not rebuilt. The current compiler does reduce build time: the 4-layer, 8,192-token program builds in 282.6 s instead of 543.6 s on the same 64-vCPU host. The output is byte-identical.

Granite 3.0-1B-A400M was 1.65–1.73× slower at 4,096 tokens. This historical result did not pass numerical qualification. Greedy local learning on a 125M-class model was 1.33× slower with K = 2 or 4 local blocks on a research branch. The main costs are large dense products, vocabulary heads, long-sequence attention and gradient scatter. Conventional libraries handle these faster than Latch’s operation implementations. These bottlenecks are among the open problems.
