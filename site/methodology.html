Methodology

How we measure, and what the results show

Every result on this site compares the same work done two ways. This page explains how those comparisons were made, what each one does and does not establish, and where the evidence is.

How we measure

Each speed result times one unit of work on a single, otherwise idle H100, once by the program Latch generated and once by a conventional PyTorch implementation. The two alternate over several rounds, so that changes in the machine affect both equally, and we report medians.

The unit is either a complete training update (forward pass, loss, backward pass, gradient clipping and optimizer step) or, for test-time adaptation, a complete block. The clock starts when the inputs are ready and stops when the GPU has finished. It excludes compilation, data loading, evaluation and checkpointing. It therefore measures execution, not the time needed to reach a given quality; that is measured separately, below.

The comparison is the fastest conventional implementation we built for the workload that passed the same numerical checks, and we name it. Where we built a CUDA-graph version, it is included. For the standard TinyMoE update we have not built one, and the captions say so; the looped TinyMoE comparison does use one.

Speed matters only if the numbers are right. Each Latch program reported here is checked against an independent reference — FP64 for the training updates — at fresh and trained states, and restarting it from a checkpoint reproduces the uninterrupted run bit for bit. Each build is a new binary and is checked again.

Different batch sizes answer different questions

A speed comparison holds the work fixed. Both implementations process the same batch with the same arithmetic, so the comparison answers one question: how much faster is this update? The answer depends on the batch. With a small batch each operation is small, overhead dominates and a megakernel gains most. With a large batch conventional kernels stay busy and there is less to gain. For TinyMoE, Latch was 5.1× faster at 2 × 512 tokens and 1.74× faster at 32 × 1024; an older measurement at the published batch of 128 × 1024 found 1.11×.

A training experiment asks a different question: which recipe reaches a target quality soonest? Here each implementation may use the batch size that suits it, because faster updates can make a smaller batch worthwhile. Comparing different batches is then the purpose of the experiment, not a flaw in it. The experiment should also run the conventional implementation at the other side's batch size, so that the effect of the batch can be separated from the effect of the compiler. We report both.

In this package Complete training update · many small routed experts

TinyMoE-200M: complete training updates

5.1× faster than the fastest compiled PyTorch at 2 × 512 tokens per update, and 1.74× at 32 × 1024; the advantage shrinks as batches grow.

The public TinyMoE-200M model, with all 199,837,056 weights, continues training on WikiText-103. Latch generates one kernel for the whole update — forward, loss, backward, clipping and AdamW. On this package, the generated update passes the independent FP64-reference audits at updates 1 and 32, trains bit for bit like the v0 option set, and restarts exactly from a checkpoint.

Compiled PyTorch64.52 ms
Latch12.57 ms

2 × 512 tokens per update. Pooled medians, 80 measured updates per arm, same H100. The v0 rc2 package measured 31.3 vs 73.4 ms

This control compiles each layer with torch.compile and uses grouped expert products, but does not replay the update as a CUDA graph; no CUDA-graph control has been built for this ragged-routing update. The advantage depends on batch size. With this package, the best measured learning recipe at 32 × 1024 tokens per update takes 79.9 ms against 139.2 ms for the compiled control (1.74×). At TinyMoE's published batch, 16 accumulated microbatches of 8 × 1024 tokens, an older historical measurement was 977.2 ms against 1,088.4 ms: large microbatches amortize most conventional overhead.

In this package Complete training update · looped layers

SMELT-style looped TinyMoE

1.34× faster than compiled PyTorch replayed as a CUDA graph. The gain is ordinary execution efficiency, not reuse from the loop.

The middle six of TinyMoE's twelve layers run twice with shared weights, a looped design adapted from the SMELT papers (no official code was found). Both implementations run the same model, objective and AdamW recipe at 32 × 1024 tokens per update.

Compiled + CUDA graph154.22 ms
Latch114.82 ms

Means over 5 alternating rounds × 3 model states, same idle H100, this package. The research branch also timed weaker controls: compiled trunk without a graph 169.60 ms, per-region compiled 197.32 ms

Looping does not create a special opportunity. Each extra pass costs Latch about 34 ms and the conventional graph about 39 ms, and an 18-layer model with distinct weights takes Latch the same time as the looped one. Inside each pass, Latch's grouped expert products are still slower than the library GEMMs, and it uses about 1.8 GiB more memory. In complete 655M-token training runs, both implementations crossed dev loss 3.50, 3.30 and 3.20 at identical update counts; Latch got there 1.31× sooner in update time each time.

The research build selected a compiler rule (rowchain) later found to permit an arena race. This package rebuilds it with the fix; the new program is bitwise equal to the research program from all three states and repeats and restarts bitwise, so those learning runs describe the packaged program.

In this package Adaptation loop, not training · sequential predict-and-learn

GradLev causal adaptation on GPT-2

3.5× faster than the strongest CUDA-graph control for a complete block of 1,024 dependent predict-and-update steps, in one kernel instead of 18,176.

While reading a 1,024-token block, the model predicts each token, scores it, and immediately updates the weights of its final MLP before the next token. Every step depends on the previous one. This adapts a published method, GradLev, to GPT-2 small (no official code was found). It measures deployment-time adaptation of one MLP, not full-model training speed.

CUDA graph, compiled step189.53 ms
Latch, previous schedule75.18 ms
Latch, this package53.98 ms

Policy P1b. Medians, 16 blocks × 5 alternating rounds = 80 samples per arm, same idle H100. Each block includes the eager trunk prefill (7.5 ms), staging, reset and read-back; the generated loop itself takes 46.2 ms

Here the changing state is small: the two adapted matrices are split across the SMs, each block owning 24 hidden units, and stay in shared memory for all 1,024 steps. The frozen 77 MB output head is too large to keep on chip and is read at every token. Under policy P1b the head's logits, online softmax and gradient share one pass; this package keeps about 23 of every 64 head row groups resident in the 50 MB L2 cache across steps, streams the rest with loads already in flight, and prefetches the next step's input rows, cutting the head pass from 41.7 to 24.4 µs per token. Every output is bitwise identical to the previous schedule. Under policy P1 (BF16-rounded gradient weights, two-pass head) the block takes 90.4 ms against 161.3 ms for its strongest control (1.79×). The learning result is modest: adaptation helps, but GradLev's extra meta-training adds nothing over the same update rule applied to an ordinary fine-tune at this scale.

Research branch Complete training update · a real limitation

E2-TTT-MLP outer training: correct, but about 3× slower

The complete 424.8M-parameter update compiles, passes its numerical checks and learns identically — and runs about 3× slower than torch.compile max-autotune.

E2-TTT-MLP is a released language model whose layers learn a memory as they read. Training it means differentiating through those inner updates. Latch generated the whole outer-training update through its normal API; its gradient error matches the published implementation, restarts are bitwise, and a 256-update continuation learned identically to the conventional executors.

Latch (2 × 2,048 microbatches)9.12 s
Published code, per-block compile8.24 s
torch.compile max-autotune (4 × 2,048)3.05 s

Seconds per 64 × 2,048-token update, means of 3 rounds × 3 updates, same H100. Each arm at its fastest runnable microbatch

Two conditions that favour a megakernel are missing here. Latch spreads each microbatch over about 5,000 barrier-separated intervals, and two thirds of its time is the memory update: many small elementwise and reduction steps that Inductor fuses into far fewer kernels than Latch's phases. And Latch keeps every saved activation in its arena, so the published microbatch of 4 sequences needs a 77.6 GB arena and does not fit on an 80 GB H100. In isolation, one layer's memory update is faster under Latch at one sequence (4.19 versus 5.48 ms) but slower at four (11.14 versus 7.10 ms). A further-tuned Latch build reached 8.79 s (2.8× slower than the control on its host); it used the compiler rule mentioned above and was not rebuilt, since it is slower either way. Compilation did improve: this package's exact lowering passes build the 4-layer, 8,192-token program in 282.6 s instead of 543.6 s on the same 64-vCPU host, with byte-identical output.

Two other measured cases point the same way: Granite 3.0-1B-A400M at 4,096 tokens, 1.65–1.73× slower (historical, not numerically qualified), and greedy local learning on a 125M-class model, 1.33× slower at K = 2 and 4 local blocks (research branch). Both lose mainly in large dense products, vocabulary heads, long-sequence attention or gradient scatter, where conventional libraries are faster than Latch's operation bodies. The capability catalogue lists every slower case.

Training to a target quality

In this experiment TinyMoE-200M was trained from random initialization on FineWeb-Edu, and we recorded the accumulated update time each recipe needed to reach validation loss 3.30. Each recipe has its own batch size and its own tuned learning rate. The Latch runs used an earlier implementation of the compiler. The program in this package performs the same updates bit for bit at batch 32, but the experiment has not been rerun with it, and we do not report projected times.

Against the fastest PyTorch implementation of the 128-sequence recipe, Latch needed 18–24% less update time on all three seeds. PyTorch can also run the 32-sequence recipe. It learned as well, but on the one seed we ran it reached 3.30 after 1,704 s, close to its own 128-sequence time; Latch took 14% less on that seed. The Latch recipe was also the only one to reach validation loss 3.20, and it ended about 0.04 nats lower on the test set.

Earlier studies at smaller batches

Before the batch-32 experiment, we asked whether much smaller batches — two sequences per update — could reach a target sooner. A single-seed pilot suggested they could. The follow-up studies did not confirm it. We keep the full record here because the pilot was once our headline.

In a single-seed pilot, Latch at 2 sequences per update reached dev loss 4.187 with 37.7M tokens and 661 s of update time, against 100.7M tokens and 960 s for PyTorch at 128 sequences. Fresh seeds on the same short schedule repeated the pattern. But changing only the learning-rate schedule to a longer horizon reversed it, and over the full long run PyTorch reached every target first on every seed. The likely cause: the short schedule's warmup was only 50 PyTorch updates, which produced large early gradient spikes. After both arms received an equal, predeclared schedule search, PyTorch still reached 3.50 and 3.30 first on all three new seeds. There is no repeatable time-to-quality win for batch 2.

The pilot's PyTorch arm was also slow: 16 microbatches of 8 sequences ran at 9.17 s per million tokens, against 4.10 s for the same batch as four microbatches of 32. The 62.5% and 31% figures from the pilot are historical and should not be cited as a benefit.
