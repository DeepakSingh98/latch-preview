Walkthrough

How a training megakernel works

Training a neural network repeats one update many times. This page builds that update from a single multiplication, shows how a GPU normally runs it, and then shows what changes when Latch compiles the whole update into one generated program, and what does not.

Diagrams marked Schematic explain mechanisms; their proportions are illustrative, not measured. Measured numbers appear only in text and tables that name their source. The figures work with a mouse, touch or keyboard; without JavaScript every step is shown in order.

01First principles

One training update, by hand

A model is a calculation with adjustable numbers called weights. A training update has five parts: an input; a prediction computed from it; a loss, which measures how wrong the prediction is; the gradients, found by working backwards, which say how each weight affected the loss; and the changed weights, each moved a little in the direction that reduces the loss.

Below is the smallest example that shows every part: one input, two weights, one target. Step through it.

The same five parts, at real scale

A real model repeats this pattern with matrices instead of single numbers. TinyMoE-200M, the main example on this site, has 199,837,056 weights. Its forward pass includes attention and a router that sends every token to two of sixteen experts (small feed-forward networks). Its update is AdamW, which keeps two extra running averages for every weight. At 2 sequences of 512 tokens, one complete update — forward, loss, backward and AdamW — is the unit of work this site measures.

Two facts carry over from the toy example. Each step depends on earlier results, so the order matters. And intermediates such as h must be stored between the forward and backward passes. The rest of this page is about how a GPU handles those dependencies and that storage.

02Conventional execution

How GPUs usually run it

A GPU runs work as kernels: programs launched by the CPU that spread one operation across the GPU's 132 streaming multiprocessors (SMs) on an H100. Frameworks such as PyTorch normally run each operation of the update — each multiply, the loss, each gradient, the optimizer — as its own kernel. A kernel reads its inputs from GPU memory and writes its result back, so the next kernel can find it.

There are three common ways to run the same sequence. Choose one to compare.

Compilation and CUDA graphs are strong baselines. Each comparison on this site uses the fastest conventional implementation we built for that workload that passed the same numerical checks, and names it. For the standard TinyMoE update that is compiled PyTorch without CUDA graphs, because no graph version has been built for it; the looped-TinyMoE and GradLev comparisons use CUDA graphs. How we measure.

At real scale the kernel count is large. For TinyMoE at its published batch size (16 accumulated microbatches of 8 × 1024 tokens per update), compiled PyTorch launched 69,394 kernels per update; a reconstruction of the original Hugging Face Trainer setup launched 228,417. Latch launched 16 generated kernels, one per microbatch, plus 17 small scalar fills. Source.

03The compiler

What Latch does

A training megakernel runs a whole update — forward pass, loss, backward pass and weight update — inside one persistent GPU program that stays resident on every SM. Latch generates that program from model code in five stages.

1 · You write ordinary PyTorch, within a supported set

A model as an nn.Module, an objective function, and an optimizer written as a pure tensor function. For TinyMoE the model is a short adapter over the public Hugging Face checkpoint that keeps every parameter name and value. Attention and expert routing use a few operations Latch provides: bf16_sdpa.sdpa, token_topk, route_order and ragged_mm. Global-norm clipping plus AdamW is plain tensor arithmetic passed to tensor_update.

Latch is not a general PyTorch compiler. Operations outside its supported set are rejected at capture or lowering, and new architectures usually need an adapter and often compiler work.

2 · Capture records the whole update as tensor operations

Capture runs the model, objective and update rule once on example shapes and records every tensor operation, in order, as a graph. Nothing is executed on the GPU yet. TinyMoE's published-batch program captured 32,010 operations.

captured = capture_module(model, objective, (tokens,), (labels, coefficients),
                          optimizer=tensor_update(update, init_state=initialize,
                                                  forward_state=True),
                          state=model_state)

Abridged from megakernel_lab/tinymoe/build.py.

3 · Latch differentiates the captured graph

From the forward graph Latch derives the backward graph — the same chain rule as steps 5–8 of the toy example, applied to every operation. It also records which forward intermediates the backward pass will read, which becomes a storage requirement in the next stage.

For expert routing, the backward pass must scatter gradients back to the tokens that chose each expert; segment sizes change every update. Supporting that gradient was work on the compiler, not on the model.

4 · Scheduling and storage

Latch groups operations into phases spread across all 132 SMs. Inside a phase, steps can be fused so their intermediates stay in registers or shared memory. Where one phase needs results produced by other SMs, Latch places a grid-wide barrier: every SM waits until all have finished. Every value that must survive across phases gets a place in one planned memory arena in GPU memory.

The plan also fixes a numerical policy. TinyMoE's practical policy keeps FP32 master weights and Adam moments and uses BF16 matrix products and attention.

5 · Generation and compilation

Latch emits CUDA from reusable hand-written operation bodies — Hopper tensor-core matrix products, attention, routing and reductions — and compiles it with nvcc on a CPU-only machine. TinyMoE is split into 16 separately compiled device units linked behind one kernel entry.

The result for TinyMoE is one cooperative kernel with 132 blocks, plus three scalar fills and five small copies per update. With this package the cold build for 2 × 512 tokens takes 283 seconds on a dedicated 64-vCPU machine, including model loading, capture, generation and linking, half the previous compiler's 544 seconds on the same machine, with byte-identical output. Source.

Each build is a new binary. Its speed and numerics must be checked again; qualification attaches to exact binaries, not to build flags.

04Limits of fusion

What fusion can and cannot save

Fusing the update into one program removes kernel boundaries and some trips to memory. It does not remove the work itself. Compare the same update both ways, then highlight each kind of cost.

What changes and what stays when the same update becomes one generated kernel
CostSeparate kernels (CUDA graph)One megakernel
Host launchOne graph replay; each kernel still starts and drainsOne launch, plus small fills and copies
DependenciesA kernel boundary between dependent stepsA grid-wide barrier where results cross SMs; every SM waits for the slowest
IntermediatesWritten to GPU memory, read back by the next kernelFused steps keep them on chip; values crossing phases still use the arena in GPU memory
Weights and optimizer stateRead and written in GPU memoryAlso read and written in GPU memory
ArithmeticThe full updateThe same update, under the stated numerical policy
Operation qualityVendor libraries such as cuBLAS and FlashAttentionLatch's own operation bodies, which can be slower

The weights do not fit on chip

A megakernel keeps some intermediates in registers and shared memory, but the model itself lives in GPU memory. For TinyMoE, the FP32 weights and the two AdamW moment buffers alone are about twenty times larger than all of the H100's on-chip storage combined, so they are read from and written to GPU memory on every update.

One kernel does not guarantee high utilization

Removing boundaries helps most when each piece of work is small, because launch and boundary costs then dominate. When the work is large, conventional execution already keeps the GPU busy, and the quality of each matrix product and attention body decides the result. Barriers can also leave SMs idle while the slowest one finishes. The catalogue lists measured cases that are slower under Latch for these reasons.

05Workloads

Three kinds of workload

Whether a megakernel helps depends on the shape of the work. Three shapes recur in the measurements.

Large regular matrices

Conventional execution

Each kernel is big enough to keep every SM busy for a long time, so launch and boundary costs are a small share of the update. Vendor matrix and attention libraries are highly tuned for exactly this case.

Opportunity

Small: fusing the elementwise glue between large operations and avoiding some intermediate round trips.

Limits

Latch's own matrix and attention bodies have to match cuBLAS and FlashAttention, and many barrier-separated glue phases add up.

Measured

TinyMoE at its published batch (8 × 1024 tokens per microbatch): 977.2 ms versus 1,088.4 ms compiled, only 1.11× faster Historical. Granite 3.0-1B-A400M at 4,096 tokens: 161.45 ms versus 97.89 ms, 1.65× slower Historical · not qualified. See also E2-TTT outer training, about 3× slower Research branch.

Many small routed experts

Conventional execution

Routing, counting, sorting tokens by expert, the ragged expert products and the gradient scatter become many small kernels. At small batches each is tiny, so boundaries dominate. Data-dependent sizes also complicate CUDA-graph capture: the strongest TinyMoE graph control on this site captures forward and backward but runs the optimizer and some bookkeeping outside the graph.

Opportunity

Large: routing, ragged products and scatter run inside one program with no host round trip and no per-kernel startup.

Limits

Latch's grouped products are slower than cuBLAS and CUTLASS grouped GEMMs; a deterministic gradient scatter is expensive when each token visits many experts; the advantage shrinks as batches grow.

Measured

TinyMoE-200M complete training update, 2 × 512 tokens: 12.6 ms versus 64.5 ms for compiled PyTorch, 5.1× faster; 32 × 1024 tokens: 79.9 versus 139.2 ms, 1.74× faster In this package.

Sequential predict-and-learn

Conventional execution

Thousands of tiny steps must run strictly in order. Even replayed from a CUDA graph, each step is still about nineteen separate kernels, and the fast state goes back to GPU memory between them.

Opportunity

Large, when the changing state is small: it can stay in shared memory, split across SMs, for the whole sequence, and all steps run in one launch.

Limits

Every step still needs grid barriers, frozen weights such as the output head are read from GPU memory at every token, and larger adapted blocks do not fit on chip.

Measured

GradLev on GPT-2 small, a complete block of 1,024 dependent steps (adaptation, not training): 54.0 ms versus 189.5 ms for the strongest CUDA-graph control, 3.5× faster In this package. Online adaptation of TinyMoE's last two expert blocks: 1.26–1.67× slower than a compiled, CUDA-graph-replayed control Research branch.
