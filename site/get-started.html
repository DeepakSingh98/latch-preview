Repository

Latch on GitHub

We intend to release Latch as open source. The repository link will appear here when the code is public.

This page describes the final research-preview package, megakernel-lab 0.9.0rc1. It has not been published: the license for the original code and the repository location are still to be decided. See the publication status and package scope.

Requirements

  • Linux, Python 3.12, PyTorch 2.9.1 built for CUDA 12.8.
  • CUDA 12.8 toolkit with nvcc, nvlink and cuobjdump, a host C++ compiler and Python development headers.
  • An NVIDIA H100 80GB to run programs. Compilation runs on a CPU-only machine (or on the GPU host with CUDA_VISIBLE_DEVICES=); the TinyMoE example builds in about 5 minutes on 64 vCPUs with eight compiler workers.
  • Built artifacts must stay at the same absolute path when moved between the build and training machines.

Install

python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install torch==2.9.1 --index-url https://download.pytorch.org/whl/cu128
python -m pip install "megakernel_lab-0.9.0rc1-py3-none-any.whl[tinymoe]"
python -I -m megakernel_lab.fast_examples list

Run this from the directory containing the supplied wheel. The source archive also supports python -m pip install ".[tinymoe]". python -I makes sure the installed package, not a source checkout, is used.

A first complete training update

This small example compiles a two-layer MLP's full training update on CPU, times it against compiled PyTorch on an H100, and checks the saved states against an independent CPU reference.

export LATCH_FAST_ROOT=/work/latch-fast
export OMP_NUM_THREADS=1 MKL_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1
export TORCHINDUCTOR_COMPILE_THREADS=1 MAX_JOBS=1

# CPU: capture the model and compile its training kernel
CUDA_VISIBLE_DEVICES= python -I -m megakernel_lab.fast_examples prepare dynamic matrix_bf16-b32 --variants latch

# H100: time engine.step against compiled/captured PyTorch; staging is excluded
python -I -m megakernel_lab.fast_examples compare dynamic matrix_bf16-b32 --rounds 2 --variants latch

# CPU: audit saved states, then report
CUDA_VISIBLE_DEVICES= python -I -m megakernel_lab.fast_examples verify dynamic matrix_bf16-b32 --workers 1 --variants latch
python -I -m megakernel_lab.fast_examples report dynamic matrix_bf16-b32 --variants latch

Other families: mlp, ordinary, ffn, mixed, adaptive and energy. The catalogue lists the tested cases and how each compares.

Run the examples

Four examples run end to end from the source archive's examples/ directory: TinyMoE-200M training, TinyMoE with a selective update cadence, SMELT-style looped TinyMoE (all complete training updates), and GradLev adaptation of GPT-2's final MLP (an adaptation loop, not training). Compile on a CPU-only machine, or on the GPU host with CUDA_VISIBLE_DEVICES=; run on an H100. Keep built artifacts at the same absolute path on both machines. Every command below was run from a fresh environment with the built wheel.

TinyMoE-200M: complete training update at 2 × 512 tokens

export TINYMOE_ROOT=/work/tinymoe
bash examples/tinymoe/quickstart.sh prepare     # pinned model + small WikiText split (CPU, internet)
bash examples/tinymoe/quickstart.sh build       # one training kernel, --rules auto (CPU)
bash examples/tinymoe/quickstart.sh train       # 32 updates, checkpoint at 15 (H100)
bash examples/tinymoe/quickstart.sh restart     # resume 15 → 32 in a new process
bash examples/tinymoe/quickstart.sh compare-restart
bash examples/tinymoe/quickstart.sh screen      # four conventional implementations
bash examples/tinymoe/quickstart.sh benchmark   # five alternating pairs vs compiled PyTorch

Selective update: experts every 16 microbatches, shared weights every microbatch

export SELECTIVE_ROOT=/work/selective
bash examples/selective_update/quickstart.sh prepare
bash examples/selective_update/quickstart.sh build          # accumulate and apply programs (CPU)
bash examples/selective_update/quickstart.sh train          # 64 microbatches (H100)
bash examples/selective_update/quickstart.sh restart
bash examples/selective_update/quickstart.sh compare-restart
bash examples/selective_update/quickstart.sh conventional   # same semantics, compiled PyTorch

SMELT-style looped TinyMoE (8 × 512 example)

export SMELT_ROOT=/work/smelt
bash examples/smelt_looped/quickstart.sh prepare
bash examples/smelt_looped/quickstart.sh build
bash examples/smelt_looped/quickstart.sh train
bash examples/smelt_looped/quickstart.sh conventional
bash examples/smelt_looped/quickstart.sh restart
bash examples/smelt_looped/quickstart.sh compare-restart

GradLev: causal adaptation of GPT-2's final MLP (one H100)

export GRADLEV_ROOT=/work/gradlev
bash examples/gradlev/quickstart.sh prepare     # GPT-2 + held-out FineWeb-Edu windows
bash examples/gradlev/quickstart.sh build       # seconds; GRADLEV_POLICY=P1b for the fused head
bash examples/gradlev/quickstart.sh run
bash examples/gradlev/quickstart.sh conventional
bash examples/gradlev/quickstart.sh benchmark
bash examples/gradlev/quickstart.sh restart

Each example's README lists the exact arguments, expected outputs and limits. A freshly built kernel is a new binary: run its checks before treating its results as qualified. The command-guide status includes the CPU audit commands; the command-guide status packages the learning tools, whose software check does not reproduce any learning study. What you can change today

Through recapture and rebuild, with the v0 TinyMoE adapter: the optimizer (pure tensor update rules such as AdamW variants, gradient accumulation and weight averaging), extra loss terms such as intermediate-layer readouts, batch and sequence length within 256–1,024 tokens in steps of 128, and learning-rate schedules staged at run time without rebuilding.

Where changes may fail or disappoint: unsupported operations are rejected; larger shapes can exceed planned shared memory; large batches and long sequences shrink or reverse the advantage; new architectures need adapter and often compiler work; general multi-GPU training is not part of the package. Every new build is a new binary that needs its own checks. See the capability catalogue.
