Workloads

Supported workloads and open problems

Each entry below is a specific configuration that we tested, not a family of models. A result for one configuration says nothing about nearby shapes or other models until those are tested too.

How to read the ratios. “Latch ÷ control” is Latch's time for a complete update divided by the time of the fastest conventional implementation that passed the same numerical checks, either compiled or replayed from a CUDA graph. Below 1.00, Latch is faster. Where a faster conventional implementation failed those checks, the entry says so and explains which comparison it uses. All times are for complete training updates, or complete adaptation blocks where stated, on one H100 80GB, excluding compilation and data loading; they measure execution, not the time needed to reach a quality target. Section 1 was measured with the final package, megakernel-lab 0.9.0rc1. Sections 2–4 cover packaged code measured with earlier releases; their checks apply to the binaries measured then. Section 5 lists research branches whose workloads are not packaged. See how we measure and sources.

1. Packaged and measured on this release In this package

Measured with megakernel-lab 0.9.0rc1 on one otherwise idle H100 80GB, against the strongest conventional implementation we measured for each workload. Every program is bitwise equal to the executor its learning results were measured with. Receipts: final-package.json; validation summary.

TinyMoE-200M complete training update

Workload
Public FlameF0X/TinyMoE-200m-2x16, all 199,837,056 parameters, forward, loss, backward, clipping and AdamW in one generated kernel.
2 × 512 tokens
latch-tinymoe build --rules auto: 12.57 ms vs 64.52 ms for compiled-grouped PyTorch, the fastest of four screened implementations (5.13×); 5 alternating pairs × 16 updates. A second host: 12.56 vs 72.01 ms.
32 × 1024 tokens (recipe Q)
79.93 ms vs 139.20 ms for C32 compiled-grouped (1.74×); the frozen pre-release Latch program took 116.48 ms. Package compiler with the study's frozen recipe harness; no packaged quickstart at this batch.
Correctness
The 2 × 512 updates are bitwise equal to a build with the v0 option set; independent FP64 audits pass at updates 1 and 32; repeat and 15→32 restart bitwise. Recipe Q is bitwise equal to its frozen executor on four states, through its restart protocol and a 512-update real-text continuation.
Control
Per-layer torch.compile, grouped expert products, fused AdamW, deterministic; no CUDA graph was built for this ragged-routing update.
Example
command-guide status (run from the installed wheel, including the arena audit: 0 violations).

TinyMoE with a selective update cadence

Workload
Complete training in two programs that share state: the experts (85% of parameters) accumulate gradients and are updated once per window; the shared weights update every microbatch.
2 × 1024, window 16
10.28 ms per microbatch vs 66.45 ms for the same semantics in compiled-grouped PyTorch on the same GPU (6.5×); 5-round paired bench 10.12 ms.
1 × 1024, window 32 (B1-FAST)
8.72 ms vs 64.0–64.7 ms for the same-semantics compiled implementation on the same GPU (7.3×). Package compiler with the study's frozen harness.
Correctness
Bitwise equal to the frozen pre-rowchain reference pairs on four states × 3 complete cycles; exact restart mid-window; 512-microbatch continuation. From a trained state the conventional counterpart agrees within 0.0024 (loss).
Semantics note
The frozen rule's expert update uses a nonstandard beta1 bias correction (1 − 0.9^t with a microbatch-equivalent counter). It equals standard AdamW from trained states but takes about 8× smaller first steps from zero optimizer state. It is kept as frozen.

GradLev causal adaptation on GPT-2 (not training)

Workload

Policy P1b
53.98 ms per complete block (trained state 54.15) vs 189.53 ms for a CUDA graph of the compiled step (3.51×); the previous Latch schedule took 75.18 ms. One kernel vs 18,176. The block clock includes the eager trunk prefill (7.5 ms), staging, reset and read-back.

90.36 ms vs 161.34 ms for the hybrid-head graph (1.79×).

Compilation time

Measured
E2-TTT 4 layers × 8,192 tokens: 543.6 / 546.8 s → 282.6 / 282.9 s on two dedicated 64-vCPU hosts (capture, 66 s, reported separately). TinyMoE example, whole build command: 544.5 → 283.1 s. Recipe Q build: 463.3 → 241.9 s.
Equivalence
Generated program.cu, manifest, bindings and headers byte-identical in every case. The saving is in lowering and capture; native nvcc time is unchanged, so the gain depends on how much of a model's build is lowering.

TinyMoE-200M, same batch per update

Model / operations
Public FlameF0X/TinyMoE-200m-2x16, all 199,837,056 parameters: 12 layers, width 384, grouped-query attention (8 query / 4 key-value heads, width 48), 16 experts with top-2 token-choice routing and no token dropping, untied 32,000-word readout, router load-balancing loss. Continued training on WikiText-103.
Historical dimensions
Batch × sequence 1 × 256 and 2 × 512; recipes unchanged and supervision_ema (exits after layers 4 and 8, faded out, plus weight averaging).
Precision
FP32 master weights and Adam moments; BF16 projections, attention and expert products. AdamW with global clipping.
Variations
Optimizer rule, loss terms, LR schedule, batch and sequence within 256–1,024 tokens (steps of 128) through rebuild.
Structure
One generated cooperative kernel (132 blocks) per update, plus three scalar fills and five small copies.
Current v0
Unchanged B2 × S512: 31.298 ms Latch vs 73.431 ms compiled-grouped, a 2.346× ratio of pooled complete-update medians over 80 updates per arm. Both arms pass unchanged independent audits at updates 1/32; native 15→32 restart is exact. See validation summary and validation summary.
Historical performance
Latch 24.1–33.5 ms vs compiled-grouped PyTorch 64.0–69.2 ms across six phase/shape windows (2.07–2.68× faster). Same H100, five alternating pairs, 80 measured updates per arm.
Historical correctness
400-update runs at both shapes and recipes; twelve full-update checks against an FP64 reference; exact restart from update 199; held-out evaluation. Qualification binds those exact binaries; rebuilds need fresh checks. No learning benefit from supervision/EMA was observed.

Historical distributed expert model on four H100s — excluded from v0

Model / operations
One fixed workload: a 100M-parameter backbone (about 210M parameters in total) with 32 experts per layer, two intermediate readout heads, vocabulary 50,257, Muon + AdamW, weight averaging (EMA). Expert-parallel across four GPUs.
Tested dimensions
Sequence length 2048 across four ranks; two heads (H2) in auxiliary and post-auxiliary phases; nearby one-head (H1) case.
Precision
Practical BF16 products with FP32 gradient sum across ranks.
Structure
Not a single kernel. 34 generated regions per update plus external NCCL communication (32 token all-to-all exchanges and one FP32 gradient sum in 33 buckets), packing and runtime work.
Performance
Schedule-weighted update 111.6 ms vs 219.4 ms for the strongest control that passed the checks (1.97×); individual phases 0.48–0.56. Clock is the slowest rank's synchronized complete update; four H100s on one host.
Correctness
Full four-rank FP64 checks pass for all four cases; transition, restart and raw/EMA evaluation pass. No new full learning trajectory was run for this runtime. Faster compiled controls that failed the checks are excluded.
Package decision
The private moe4 runtime, runner, CLI and examples are excluded from v0. Historical four-H100 evidence is retained for context and is not new v0 qualification. The required WeightEMA utility was ported into tinymoe. See package scope.

Small-batch TinyMoE learning

Scope
TinyMoE from random initialization on FineWeb-Edu. In a single-seed pilot with a 131,072,000-token schedule, Latch at 2 × 1024 tokens per update reached validation loss 4.187 with 62.5% fewer tokens and 31% less training-update time than the compiled PyTorch configuration used in that pilot (128 × 1024 as 16 microbatches of 8). At 1 × 1024 it was not faster in time.
Status
Pilot not confirmed The pattern repeated on fresh seeds with the same short schedule (0.45–0.70× the conventional time where both arms reached a level), but reversed when only the learning-rate schedule changed (1.08–1.68×). With each arm's schedule tuned independently, conventional training reached every target first (Latch needed 1.27–1.59× the time, or did not reach the target). Frequent small updates remain more token-efficient, about 1.2–1.4× fewer tokens at dev 3.30–3.50, but that has not translated into less training time in any measured TinyMoE recipe. The pilot's conventional arm was also about 2.2× slower per token than the strongest batch-128 PyTorch measured later. These follow-ups ran on research branches.
Package
The v0 learning tools passed a 128-update software check with exact restart and FP64 audits of fresh updates 1 and 2 only; they reproduce no learning study.
Evidence
Learning studies · smallbatch-pilot.json (pilot extract) · learning-study summary (frozen before the follow-ups)

TinyMoE at other shapes

Historical scope

5. Unsupported

  • GPUs other than the H100. Generated code targets SM90 (Hopper) and every measurement is on H100 80GB.
  • Arbitrary PyTorch programs. Latch captures a defined set of operations; others are rejected. New architectures usually need an adapter and compiler work.
  • General dynamic shapes. Each binary is built for static shapes, except the bounded batch dimension of the dynamic MLP example.
  • General multi-GPU training. The historical fixed four-H100 runner is not shipped. The package makes no general distributed-training claim; see package scope.
  • General inference and generation. The package measures one forward loop, GradLev's causal adaptation, through vector_resident: batch-1 products, last-dimension reductions, small carries, at most 1,024 steps, a fixed grid of 132 CTAs, an L2 budget tuned for the H100. Other inference and generation programs are present as capture code but are not qualified or measured.
  • Convolutions, nested loops, dropout and attention padding masks as package features. Compiler code for these is present, but it has not been qualified or measured for this package.
  • Moving built artifacts. Exact restart requires the same binaries at the same absolute paths and runtime.
  • One-click builds. Large models need explicit build options today.

6. Where contributions would help

Each target comes from a measured limitation above.

  1. Long-sequence attention. On Granite at 4,096 tokens, Latch's attention takes about 20 ms per update against about 14 ms for FlashAttention-2.
  2. Gradients of repeated gathers. Top-8 routing sends each token to 8 experts; Latch's deterministic backward scatter takes about 32 ms where conventional code takes about 5 ms. The multiplicity is known in advance, so a direct per-row sum should be possible.
  3. Fewer barrier-separated phases. Granite's update has about 1,200 small elementwise, normalization and routing intervals costing about 25 ms; in E2-TTT, standalone elementwise phases take 55% of the memory region at 4 sequences. Fusing them is open work.
  4. Smaller activation arenas. Latch keeps every saved activation in one arena without recomputation; E2-TTT's published microbatch does not fit on an 80 GB H100.
  5. Feed-forward blocks remain 1.24–1.45× slower than compiled PyTorch.
  6. Faster lowering. This package halves build time with identical output (TinyMoE example 544 → 283 s on 64 vCPUs), but lowering is still single-threaded Python and remains the largest part of most builds.
  7. Automatic build configuration. Choosing device units, outlining and shared-memory reserves without hand-set flags, so a new shape just builds.
  8. Large-batch efficiency. The TinyMoE advantage is 5.1× at 2 × 512 and 1.74× at 32 × 1024 per update with this package; an older measurement at the published batch (16 × 8 × 1024) was about 10%, and on Granite at 4,096 tokens Latch remains slower. Larger batches still reduce the advantage.
  9. Numerical checks for BF16 expert models. At trained states every valid BF16 implementation of Granite is 25–33% (median) from FP64 on single accumulation microbatches; a better-calibrated, pre-registered criterion is needed.
  10. New models and learning algorithms. Ports of other public models, and learning algorithms that make use of frequent small updates.
